XCS signs its in-game module with Ed25519. The loader verifies that signature before executing the downloaded module.

## Verification flow

1. **Build** — XCS packages the module and signs the build with an Ed25519 private key.
2. **Serve** — The XCS server stores and returns the signed module and signature.
3. **Verify** — The loader checks the signature against its embedded public key.
4. **Execute** — A module with a valid signature runs in the loader’s Luau environment. A failed verification stops that module from running.

```text
Signed build → XCS server → loader signature check → execution
```

## What signing protects

- **Integrity** — Modifying the signed module causes verification to fail.
- **Authenticity** — A valid signature ties the module to the private key corresponding to the loader’s embedded public key.
- **Signing-key separation** — The serving system does not need the private key to distribute an already signed build.

## Trust boundaries

Signature verification does not evaluate whether authorized source code is safe, guarantee service availability, or protect a game after its loader or embedded public key is replaced. Keep the starter kit, server scripts, Roblox account, and any API credentials protected through normal access controls and review practices.
